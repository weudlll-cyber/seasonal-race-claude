# RaceArena — Branding System

**Status:** Phase 1 Steps 1 and 2 built and owner-confirmed.
- Step 1 (`backup/brand-step1` → `0ba867f`): active session key, profile selector, CSS-var injection, transition tint.
- Step 2 (`backup/brand-step2` → `8e91ab3`): corner logo overlay (bottom-right, size/opacity controls).

**Phase 2** (canvas overlays) and **Phase 3** (trackside banners, racer livery) are not built; see §5.

---

## 1. What branding is

Branding is an optional feature that lets a game-master dress a session of races in house colors — a
named event, a logo, and two accent colors that tint visible UI elements. It is deliberately not the
main feature of RaceArena; it sits in the background. The intended use case is a recurring tournament
or sponsored event where the operator wants consistent visual identity across screens. Phase 3
(trackside banners, racer livery) has been **cut** by owner decision and will not be built.

## 2. Current built state (Phase 1 Steps 1–2, owner-confirmed 2026-06-12)

### Branding profiles

Profiles are created, edited, and deleted in **DevScreen → Branding** (`BrandingProfiles.jsx`). The
form is full CRUD. Every saved profile has the following fields
([`BrandingProfiles.jsx:17–29`](../client/src/screens/DevScreen/sections/BrandingProfiles.jsx#L17-L29)):

| Field | Type | Notes |
|---|---|---|
| `name` | string | Required. Display name for the profile (e.g. "Spring Cup"). |
| `eventName` | string | Required. The event title shown in UI elements. |
| `subtitle` | string | Optional secondary line (e.g. season or sponsor name). |
| `primaryColor` | string | Hex color. Drives `--brand-primary` CSS var. Default `#e63946`. |
| `secondaryColor` | string | Hex color. Drives `--brand-secondary` CSS var. Default `#f4a261`. |
| `sponsorText` | string | Sponsor credit text. Stored but not yet displayed anywhere. |
| `logo` | string | Base64 data URL of an image. Shown as corner logo overlay during races (see below). |
| `isDefault` | boolean | UI star indicator only — **does NOT drive activation** (see below). |
| `logoMaxHeight` | number (px) | Max height of the corner logo. Range 40–160. Default `90`. |
| `logoOpacity` | number (0–1) | Opacity of the corner logo. Default `0.9`. |
| `logoCorner` | string | Fixed `'bottom-right'`. Stored on the profile but no UI selector (corner is not configurable). Top-right was removed after a browser eye-check — it overlaps the start countdown numbers and the "Race Plan" badge; bottom-right is the only HUD-free corner in normal play. |

Each saved profile gets an `id` generated by `newId()` (`storage.js:158`) prepended on save.

### Storage

Both the profile list and the active-session pointer live in **`window.localStorage`** — not on the
server.

| Key | Constant | Default | Content |
|---|---|---|---|
| `racearena:branding` | `KEYS.BRANDING` ([`storage.js:13`](../client/src/modules/storage/storage.js#L13)) | `[]` | Array of profile objects |
| `racearena:activeSession` | `KEYS.ACTIVE_SESSION` ([`storage.js:14`](../client/src/modules/storage/storage.js#L14)) | `{ activeBrandingProfileId: null }` | Active profile id or null |

**Implications:**
- Per-browser, per-device. A profile created on one machine is not visible on another.
- The browser's localStorage quota is typically ~5 MB. Base64 logos are large (a 200 KB PNG becomes
  ~270 KB as a data URL). A few logos can consume the quota; the app logs a warning and silently
  skips the write if the quota is exceeded (`storage.js:45–47`). Operators with large logos should
  compress before uploading.
- No server backup. Clearing browser data deletes all profiles.

### Activation (SetupScreen selector)

SetupScreen reads both `KEYS.BRANDING` and `KEYS.ACTIVE_SESSION` via `useStorage`. A `<select>`
dropdown appears in the header **only when at least one profile exists**
([`SetupScreen.jsx:447–465`](../client/src/screens/SetupScreen/SetupScreen.jsx#L447-L465)):

```
Branding: None ▼
           Spring Cup
           Winter League
```

Selecting a profile writes `{ activeBrandingProfileId: "<id>" }` to `KEYS.ACTIVE_SESSION`.
Selecting "None" writes `{ activeBrandingProfileId: null }`.

**Important:** the `isDefault` flag on a profile is a cosmetic star in BrandingProfiles — it is set
by "Set as default" but is **not read anywhere** to drive automatic activation. The game-master must
explicitly select a profile in the SetupScreen selector to activate it.

### CSS-variable injection

Whenever the active profile changes, a `useEffect` in SetupScreen writes two CSS custom properties
directly onto `document.documentElement.style`
([`SetupScreen.jsx:163–174`](../client/src/screens/SetupScreen/SetupScreen.jsx#L163-L174)):

```js
root.setProperty('--brand-primary', profile.primaryColor);
root.setProperty('--brand-secondary', profile.secondaryColor);
```

When the selector is set to "None", both properties are **removed** (not set to a default):

```js
root.removeProperty('--brand-primary');
root.removeProperty('--brand-secondary');
```

Because these are inline styles on `<html>`, they persist across React navigation (SPA routing does
not reload the page). They are cleared only on full browser reload, at which point SetupScreen
re-mounts and re-injects from the stored active session.

The `:root` block in `main.css` does **not** define `--brand-primary` or `--brand-secondary` as
static values ([`main.css:18–19`](../client/src/styles/main.css#L18-L19)). Each CSS use-site
provides its own fallback via `var(--brand-X, <fallback>)` so that an unset variable never changes
the look of unbranded sessions.

### Visible result (what actually changes in the browser today)

**Screen-transition fade color** — [`TransitionOverlay.css:13`](../client/src/contexts/TransitionOverlay.css#L13):

```css
background: var(--brand-primary, #000);
```

With a profile active: the full-screen fade between screens flashes in the brand's primary color.
With no profile: the fade is black, identical to before branding was added.

**Corner logo overlay** — [`BrandLogoOverlay.jsx`](../client/src/screens/RaceScreen/BrandLogoOverlay.jsx),
rendered as a sibling DOM element inside `.race-canvas-wrapper` in `RaceScreen/index.jsx`:

- Reads the active profile's `logo`, `logoMaxHeight`, and `logoOpacity` fields.
- Positions itself **bottom-right** (`bottom: 16px; right: 16px`) via `CORNER_STYLES` inline style.
- `pointer-events: none`; `drop-shadow` filter for legibility on any background.
- Renders `null` when there is no active profile or the profile has no logo set.

```jsx
<div className="brand-logo-overlay" style={corner}>
  <img ... style={{ opacity: profile.logoOpacity ?? 0.9, maxHeight: (profile.logoMaxHeight ?? 90) + 'px' }} />
</div>
```

These are the **only** two visual changes currently wired to branding. Everything else
(`sponsorText`, `eventName` display in RaceScreen/ResultScreen, broader UI tinting) is
stored but not yet displayed — see §4.

## 5. Deliberately out of scope / deferred decisions

### Phase 2 — canvas overlays (deferred, not cut)

Any branding that appears **inside** the race canvas (e.g. coloring the `drawTitle` call, a
countdown overlay in brand colors) touches the requestAnimationFrame render loop and the
CameraDirector pipeline. This is a separate engineering concern and is deferred until after Phase 1
DOM work is complete. No canvas/draw-function files have been touched by Phase 1.

### Phase 3 — trackside banners and racer livery (CUT)

Per owner decision, trackside banners and racer livery are not in scope. These would require canvas
rendering changes and new asset pipelines. They will not be built.

### Open product decision — localStorage vs server-side brand store

Branding data currently lives in `localStorage` (per-device, no sharing, ~5 MB quota). If branding
ever needs to be shared across machines (e.g. multiple operator tablets at an event) or if the logo
quota becomes a practical problem, the profiles would need to move to the server
(`POST /api/branding-profiles` or similar). This is not urgent for the current single-device use
case and has not been decided. Logged here so it is not forgotten.
