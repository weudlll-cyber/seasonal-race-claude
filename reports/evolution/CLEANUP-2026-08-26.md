## 2. HOW "CONTAINED" WAS ESTABLISHED — two tests, not one

`git merge-base --is-ancestor origin/BRANCH origin/master` returned true for six. That is decisive
about HISTORY: every commit on the branch is in master's history, so nothing on them is unreachable.

**It is not decisive about the working tree**, and that is the trap the spec points at. A file can be
authored on a branch, merged, and later deleted from master's tip; the branch stays an ancestor while
the file is gone from the tree a reader checks out. So a second test ran on all six — the set of
paths on the branch tip minus the set of paths on master's tip, via `git ls-tree -r --name-only` on
each side and `comm -23` over the sorted lists.

**All six returned empty.** Every file on every contained branch's tip is also on master's tip.
Containment holds in both senses, and deleting those six cost nothing at all.

## 5. THE ORDER, WHICH WAS THE POINT

The spec's rule — *anything unique is pushed or archived before anything is deleted* — was executed
literally, and the register requirement (*tag and register entry in the SAME push*) shaped it:

1. Both annotated tags created locally, at the branch tips.
2. The register section written into `docs/TAGS.md` on a branch and merged to `master` **locally**.
3. **One atomic push:** `git push --atomic origin master archive/runin-chance-set-1
   archive/runin-seed13-anatomy-1`. Atomic because a tag reaching origin ahead of its register line
   leaves `check-tags` red on `master` for the interval, and a tag pushed without its reason is
   precisely what the register exists to prevent.
4. Reachability re-verified at origin with `git ls-remote --tags` **after** the push and **before**
   any deletion — 4 matching refs, the tag object and its peeled commit for each.
5. Only then the eight deletions, origin first, then local.

`master` was never red, and no branch was deleted while its unique content lived in one place only.

## 6. A WRONG ANSWER OF MINE, RECORDED RATHER THAN DELETED

**The first containment sweep reported eighteen files as DIFFERING between
`diag/runin-chance-set-1` and `master`, including `.gitattributes`, `.gitignore` and
`.vscode/settings.json`. Every one of those was false.** The loop compared blob hashes by calling
`git rev-parse "origin/BRANCH:PATH"` per file. Under Git Bash on Windows, MSYS path conversion
rewrote the `rev:path` argument — the error text shows `origin\master;.gitattributes`, with the
slash flipped and the colon turned into a semicolon — so `rev-parse` was answering about a
nonexistent revision, and the mismatch it returned was read as a difference.

It was caught because the answer was **implausible against a cheaper test already run**:
`git diff --name-status origin/master origin/BRANCH` had not listed `.gitattributes` at all, and both
statements cannot be true. The sweep was redone with `git diff --diff-filter=A` plus `git cat-file
-e`, which do not take a `rev:path` argument in that form.

**The general rule, which is why this is in the report:** on this platform a `rev:path` argument is
not safe in a Bash-tool loop, and a containment answer that disagrees with a plain `git diff` is the
tool being mangled, not the branches differing. The same shape as CLEANUP-2026-08-24's orphan count
that came back zero — a instrument failing silently and returning a confident wrong number. Had the
implausible result been trusted in the other direction, two branches would have been kept for no
reason; had the tool mangled the *added-files* query instead, five instruments would have been
deleted.

## 10. PROPOSALS — none ordered, none built

### A — Give `check-tags` a second question: does the register's SHA match the tag?
`check-tags` verifies that a declared name exists at origin and that an origin name is declared. It
does **not** check the SHA in the declaration against the tag's actual target — the parse only
requires a 6-to-40-character hex token. A register line could name the wrong commit forever and stay
green. Cost: a few lines beside the existing parse, which already captures the SHA. Risk: legacy
entries recording a tag-object SHA where the peeled commit is meant, which would need a one-time
sweep before the check could be turned on.

### B — Start the eased-admit piece from `archive/runin-chance-set-1` rather than from scratch
The owner asked for an eased admit on 2026-08-26. The predicate, its sweep driver, its summariser and
its warning measurement are all on that tag, together with the price and the one regression. Rebuild
would re-derive four instruments to reach numbers that already exist.

### C — MINE: make the branch survey a script, not a habit
This block ran, by hand, the same six queries CLEANUP-2026-08-24 ran by hand: ancestry, tip-path
difference, added-files, unpushed-local, stashes, worktrees. Both sweeps found a real stranded
instrument; both nearly missed it. A `scripts/branch-census.mjs` printing the three-way verdict per
branch would turn a judgement call into a reading, and would have made §6's mangled `rev:path` a
tested code path instead of an ad-hoc loop. It should refuse to print a verdict it could not
establish, per Lesson 187, rather than defaulting to CONTAINED.

### D — MINE: teach the census the "live branch" concept so it cannot recommend sweeping one
The single most dangerous outcome of an automated branch sweep is deleting the one branch that is
waiting on the owner. Right now the only thing preventing that is prose in `docs/TAGS.md` that this
block just had to add. A branch could carry the fact itself — a `live/` prefix, or a marker file the
census reads — so "waiting on the owner's eye" is a property of the branch and not of someone having
read the right paragraph.

### E — MINE: record instrument provenance next to the claim, not only in the report
Both stranded harnesses were found by sweeping branches. Neither would have been found by reading the
claim that depends on it: `RACE-ACTION.md` §6 cites `sweep.mjs` results without naming `sweep.mjs`,
and the INDEX cites the chance-set numbers without naming `chance-set.mjs`. If a claim that rests on
a measurement named its instrument by path, a grep would answer "does the instrument behind this
number still exist" in one step — and this whole class of near-miss becomes a guard rather than a
sweep.
