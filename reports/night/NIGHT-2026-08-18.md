## TOMORROW'S LIST — ordered by what you would see

### 1. First-admin setup cannot succeed. Nobody can install this game on a new machine.

**What it is.** The client sends the bootstrap token in the request **body**; the server reads it
from the **header** and nowhere else, by explicit design.

```js
// client/src/services/authApi.js:44
body: JSON.stringify({ username, password, token })

// server/src/auth/authRouter.js:54
const token = req.get('x-bootstrap-token') ?? '';   // "header only, never body"
```

The token therefore arrives as `''`, `constantTimeEqual` fails, and the server answers
**403 `setup not available`** — the same message it gives when no token is configured at all. The
operator sees a setup screen that refuses a token they just typed correctly, and the message points
at the wrong cause.

**What it would change.** One line in the client: send the header. Plus one end-to-end test that
proves body-only is rejected and header-is-accepted — because there is not one, which is the next
item.

**What happens if it is left alone.** Nothing, for you. The marker file exists and your admin user is
in `users.json`, so you will never call this path again. It fails the first time anyone else installs
it, or the first time you set up a second machine, or after any restore that does not carry
`users.json`.

**Why I did not fix it.** It is server-and-client behaviour on the auth path. Your standing rule is
that anything that could change the game gets listed. This changes what a request looks like on the
wire, and I could not prove it safe without running a real end-to-end setup, which needs a token you
own.

*(This one was first raised in `reports/audit/PROJECT-AUDIT-2026-08-18.md`, an untracked file already
in your working tree — see item 15. I re-derived it from source rather than taking it, and it holds.)*

### 2. Both test suites are green, on either side of the break in item 1.

The server suite contains this test, and it passes:

```js
it('setup: token in req.body only (not header) → 403 — header-only enforcement', …)
```

**It asserts that the server rejects exactly what the client sends.** The client's own test mocks
`fetch` and asserts the parsed response — it cannot see which channel the token travelled on.

**This is the shape of the answer to your question, in one file pair.** Each side is correct about
itself. Each side is tested. The contract between them is tested by neither, and the suite that
comes closest is *enforcing* the mismatch. 4091 client tests and a full server suite go green over a
feature that cannot work.

**What it would cost.** One integration test. **If left alone:** the same split-brain can recur at
every API boundary, and the green suites will keep saying it has not.

### 3. A missing track geometry reads as a CLOSED track — in the shipped game, at three places.

```js
// client/src/screens/SetupScreen/SetupScreen.jsx:204, 415, 435
const geom = getTrack(track.geometryId);
return geom ? !geom.closed : false;
```

`trackLoader.cacheTrackGeometry` has a 3000 ms timeout and `catch { return null }`, and its caller
throws the result away with `Promise.allSettled`. So the **track list caches successfully while a
geometry silently does not**, and the open/closed decision — which picks laps versus time — defaults
to closed.

**What you would see:** an open track that runs as a laps race, with the right name, the right
picture, and no message anywhere.

**This is not new, and I am not claiming it.** `client/e2e/appReady.js` documents this exact
mechanism, written 2026-08-16 when it was diagnosed as the browser suite's flake. **What is new is
where it lives: this is shipped code, not test-only.** The helper frames it as why specs flake; the
same three lines run in your browser. You have not seen it because your API answers in milliseconds.

**Cost:** small — surface the failure rather than defaulting. **If left alone:** it stays invisible
until the day the backend is slow, and then it looks like a race-mode bug.

### 4. Custom surface classes vanish silently when the backend is slow.

`surfaceClassLoader.fetchServerSurfaceClasses` — 3000 ms timeout, then `catch` → the localStorage
cache, which is empty on a cold profile → **code defaults only**. Your custom classes and your
overrides are simply not there, in the Setup filter and in the trails.

**Measured limit:** they do not reach physics. `registry.loadServerClasses` feeds trail/particle
effects and the Setup filter. So this is a picture-and-choice defect, not a race one.

**Cost:** small. **If left alone:** a track looks wrong and the reason is a fetch that failed three
seconds earlier.

### 5. A corrupt stored config silently reverts to defaults, with no message.

`storageGet` wraps `JSON.parse` in `catch { return fallback }`. Every loader in the app goes through
it. One malformed byte in `racearena:cameraConfig` and **your entire camera tuning is gone**, replaced
by the shipped defaults, with nothing on screen and nothing in the console.

**Cost:** one `console.warn` would make it loud; a banner would make it obvious. **If left alone:**
the day it happens you will report that the camera changed by itself, and there will be no evidence.

## THE HONEST SENTENCE

**The game is sound. The accounting around it is not — but not in the way that phrase usually
means.**

Zero of tonight's 24 findings touch the race. Four fingerprints, measured six times across two
branches, never moved. The mirror census — the largest open worry in this area — closed to a
residue that is entirely *decisions you have not been asked yet*, not defects. The 452-key sweep for
a dead control found nothing. **On this evidence your months of testing and our nights of finding
problems are not in conflict at all: you have been testing the race, and the race is fine.**

**What is weak is everything that is not the race, and it is weak in one specific way: it fails
quietly and defaults confidently.** Item 1 is the pure case — a feature that cannot work, sitting
behind two green suites, one of which enforces the break. Items 3–6 are the same shape in the
running app: five separate places where data that failed to arrive is replaced by a plausible
default and nothing says so. That is why you do not find these and we do. **You exercise the paths
that work. These defects live only on the paths that fail**, and on your machine nothing fails.

**So: better than "the game is sound and the accounting is not".** The accounting *about the race*
is genuinely strong — that is what four immovable fingerprints across two blocks of edits mean.
What is thin is the accounting about everything *around* the race: the auth path has no contract
test, five failure paths have no voice, and three guards describe a scope wider than the one they
walk. None of that is a hole in the game. All of it is a hole in your ability to be *told* when
something has gone wrong, which is exactly why the defect count you have observed is low and stays
low right up until it is not.

## PROPOSALS

### Proposal A — give the failing paths a voice (small, and it changes the picture, so it is yours)

Five places (items 3–6, and `storageGet` under them) substitute a default for data that failed. Not
one of them tells anybody. The proposal is deliberately **not** to change any fallback — changing
what happens on failure is a behaviour change and needs your eye — but to make each one **say so**:
one console line with the cause, and for the two that change what you see (a missing geometry, a
missing surface class) one visible mark.

**Why this and not "fix the fallbacks":** the fallbacks are mostly right. An app that refuses to
start because one geometry timed out is worse than one that runs. The defect is not the fallback,
it is that the fallback is indistinguishable from success. **Cheapest possible version:** a single
shared `reportDegraded(source, cause)` helper, five call sites, and a Dev Screen line listing what
degraded this session. That is a day, and it converts the whole class from invisible to obvious.

### Proposal B — one contract test per API boundary, starting with setup

Item 2 is not "we forgot a test". It is that **client and server are each tested against their own
belief about the contract**, and no test exists at the seam. The setup path is the proof: the server
suite asserts header-only, the client sends body, and both are green.

**The proposal:** for each API route the client calls, one test that drives the real client function
against the real server handler and asserts the transport, not just the payload. There are not many
routes. Starting with `/setup` closes item 1 permanently rather than fixing it once.

**Why it is worth more than its size:** it is the only proposal here that would have *prevented* the
finding rather than caught it late, and the same seam exists at every boundary this app grows.

### Proposal C — make each guard's routing equal its declared scope, or shrink the declaration

Items 10, 11 and 13 are one defect in three places: a guard says it covers X and routes on a set that
is not X. Each individually is minor and CI covers for all of them. Together they erode the thing the
declaration system was built for — **that what a guard believes is visible without reading it.**

**The proposal is the cheap half:** do not widen the guards. Make the declaration true. Add the repo
root to two `dirs`, name test-only edits in one blind list, and state `check-index`'s three
directories as a decision with the 329-file number beside it. That is an hour and it restores the
property that a declaration can be trusted. Widening `check-index` to eleven more directories is a
separate, larger question and should not ride along.
