## Piece 4 — TrackEditor.loadmode timeout, investigation

**Not touched in code.** Measurement + diagnosis only, per the task's
"investigation, drop if the night is short."

### The measurement

Three runs, all pass, timings from the JSON reporter:

| Context | Longest loadmode test | File wall time |
|---|---|---|
| File alone (`--pool=forks`, 1 file) | 387 ms | 4.55 s |
| TrackEditor group (8 files) | 636 ms (1.6× alone) | 8.43 s |
| Full suite (203 files, 4000 tests) | **1778 ms (4.6× alone)** | 5921 ms |

Under the full suite, the loadmode file overlaps in wall-clock time with FIVE
other test files (framingRule, ResultScreen, ResultScreen.ceremony,
racePlanner, standingsInvariant, startBoardRendering) — vitest's fork pool
runs many test files concurrently, defaulting to num-CPUs workers, and each
worker carries its own jsdom + module graph.

### What makes this file specifically slow under the full suite

Every one of the six slowest loadmode tests is a **React click → waitFor →
async assertion chain** on a large component:
- 387 → 1778 ms: "Save calls updateTrackOnServer (PUT) with the server track id"
- 178 → 693 ms: "first-time geometry save…"
- 175 → 657 ms: "second save (existing geometryId) preserves…"
- 141 → 605 ms: "Save calls PUT (not POST) even when track has no background"
- 141 → 565 ms: "first-draw on no-background track…"
- 15 → 481 ms: "title shows 'New Track'"

The pattern: `render(TrackEditor)` (1066-line component that pulls the
`useTrackIO`/`useServerTracks` graph) → `fireEvent` → `waitFor` polling for a
mocked-API state update. **`waitFor` polls a macrotask timer that stalls
under CPU contention**, and TrackEditor's render is heavy enough to lose
worker time to whoever else is running.

The 3.1 s "worst sample" in the task is one bad realisation of the same
phenomenon — my run peaked at 1.78 s, a busier machine or noisier concurrent
files hits 3+ easily. The distribution is inherent to the pool topology, not
to the test.

### Honest answer

**The budget IS too tight for a suite that runs 203 test files through a
default fork pool.** The loadmode file itself is not intrinsically slow — its
worst test is 387 ms with the whole worker to itself.

**The fix, ranked by cost:**

1. **Reduce parallelism for THIS file only** — a `test.pool` override or a
   `test.sequential.setupFiles` route in `vitest.config.js`, or split the
   loadmode file into a folder that the pool config gives fewer workers. It
   fixes the tail without slowing the median. **Cost:** ~500 ms added to
   the full run.
2. **Mock `useTrackIO` directly** rather than mocking its underlying
   `trackApi.js`. The chain the async assertions traverse would be one link
   instead of three. **Cost:** 3-4 tests need rewriting; some coverage of
   the useTrackIO flow moves elsewhere.
3. **Raise the timeout** — explicitly the task rules this out. It would
   only hide the next slowdown.

**Not-found-here map:** the 5 s number is vitest's default `testTimeout`;
neither `vitest.config.js` nor the loadmode file overrides it (grep for
`testTimeout|hookTimeout|5000` inside them returns nothing). The fix, if
taken, belongs in `vitest.config.js` alongside the existing `retry: 0`
guidance, and should NAME the loadmode file specifically so the general
budget is unchanged.
