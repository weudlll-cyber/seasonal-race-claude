> membership buys a median 2.28 s of warning and the width spends none of it.

**2. Undelivered track changes.**

> supported mechanism that delivers it. Your garden-path beetle is the live case. PIECE 5 changes the
> icon and description in the one place that owns them and will state plainly whether your own
> installation would ever see it.
>
> **THE QUESTION: should a shipped-data change be deliverable to an existing installation at all, or
> is "new installs only" the intended behaviour?**

**3. The server suite's parallelism — restore the flag, or forgive the timeouts?**
> PIECE 1 measured it: putting `--no-file-parallelism` back takes every one of 673 tests under 2.5 s.
> But `20868394` dropped it deliberately as part of making test isolation real, and restoring it must
> not restore that reasoning — it would be serialisation for SPEED, with isolation still carried by
> the per-file stores. One thing is unestablished and blocks it: `verify.mjs` claims the files share a
> real sqlite session store. If that is still true, parallelism is a correctness bug too.
>
> **THE QUESTION: should the server suite go back to running its files one at a time — or should the
> gate learn to report a timeout-only failure as INCONCLUSIVE rather than as a pass or a fail?**

**4. The harness's camera-seed default.**
> Since your decision of 2026-08-23 the browser derives the camera seed from the race seed, while the
> shared harness still defaults to a constant no race can produce. Every harness claim about what a
> particular race LOOKS LIKE is measured on a camera the product cannot make. The fingerprints pin
> that constant on purpose, so changing the default is not free.
>
> **THE QUESTION: should the harness default follow the browser, with the fingerprints re-minted once
> deliberately — or stay pinned, with the instruments that make look-like claims switched over
> individually?**
