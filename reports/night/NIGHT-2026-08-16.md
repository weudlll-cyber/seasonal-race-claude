## PIECE 2 — the reset badge was never a product defect

The only e2e failure that performed a real UI action and got a wrong answer. **Diagnosed before
anything was changed, and the diagnosis reversed the expectation: Reset-to-Default works.**

**Defect one, and it is a hazard rather than a nuisance.** The test's setup and cleanup fetched
**`http://localhost:4000` — hardcoded, the owner's API** — from inside `page.evaluate`, while the
suite runs against its own isolated instance on another port. Run in isolation it failed at **line
203**, not at the badge assertion at all: no override was ever created, so the Reset button correctly
did not exist. In a full-suite run it got further only because **the test above it had left an
override behind**.

**Whenever the owner's API was up on 4000, this spec was `PUT`ting an override into his live
surface-classes and `DELETE`ing from them in its `afterEach`.** Those two calls were the last
hardcoded ports in the suite.

The setup was also wrapped in a `try/catch` that swallowed its own failure — which is how it ran on
leaked state for two months. It is now `page.request` (carrying the browser context's cookies)
against the run's own API, and its result is **asserted**.

**Defect two.** The final assertion was `expect(page.getByText('Modified')).not.toBeVisible()` — a
**page-wide** query. With any other class overridden it resolved to two elements, and a strict-mode
violation **aborts** an assertion immediately rather than retrying, so it never waited the 5 s it
asked for. It now asserts the Reset-to-default control is gone — rendered only for a `modified`
class, so it is the statement *"this class reverted"*, scoped by construction.

**Proof, in the required order: fails before (line 203 isolated, line 220 in a full run), passes
after.** Nothing minted; no source outside `client/e2e/` touched.

## PIECE 4 — the server tree is audited, and what it found is named

The gate only ever ran in `client/`. **One script, not two (R13)** — the new rule needs the same
anchor, message and blind list, so `--tree=` was added rather than a second script; the default with
no flags is byte-for-byte the old behaviour.

**It now annotates reachability** by re-running with `--omit=dev`, because *high severity* and *can
reach the running product* are different questions. Where the second pass cannot be parsed it prints
**UNKNOWN** rather than claiming dev-only — it never asserts safety it did not establish.

**4 un-allowlisted HIGH on the server tree. Exactly one reaches production:**

| reach | advisory | path |
| --- | --- | --- |
| **PRODUCTION** | `GHSA-mwp4-54f8-5fhr` — ip-address decodes leading-zero octets as decimal; SSRF / trust-boundary bypass | `express-rate-limit@8.5.2 → ip-address@10.2.0`; affects how client IPs are bucketed for rate limiting — the auth limiter is the exposed surface |
| dev-only | `GHSA-28wg-ghj8-5hjv`, `GHSA-2v37-7h3g-55p8` — nanoid infinite loops | `vitest → vite → postcss → nanoid` |
| dev-only | `GHSA-r28c-9q8g-f849` — postcss path traversal via sourceMappingURL | `vitest → vite → postcss` |

Plus 3 moderate and 1 low. **`npm audit fix` claims a non-breaking fix for all four; none was run.**

**Report-only, with a reason and an end date.** They are **not allowlisted** — the allowlist takes an
entry only where there is *no* fix, so allowlisting a fixable advisory would misstate why it is
tolerated. And they are not fatal tonight because failing would turn master red over untriaged
dependency bumps on a tree that had never been audited — which is how a red build becomes something
people learn to ignore. Drop `--report-only` to flip it to a gate.

**The React-Router entry stays, and not for the reason I expected.** `GHSA-qwww-vcr4-c8h2` is no
longer reported at all — the client tree audits **completely clean, 0 vulnerabilities of every
severity**. But the entry's own removal condition is *"once react-router ships a patched >8.2.0 and
bump to it"*, and the installed version is **7.18.2 — inside the vulnerable range 7.12.0–8.2.0**.
Nothing was bumped; the advisory simply stopped being emitted. **The condition is not met**, so the
entry stays: an inert allowlist line costs nothing, and removing it because a feed went quiet would
mean it silently stops protecting if the advisory returns.

## PIECE 5 — the six columns that arrived through `...r`

Six of the sixteen hashed columns came from spreading a racer result object, so their names were
`runSingleRace`'s field names: rename a field there and a **hashed column** is renamed, silently, for
a race that did not change. That is exactly what cost a day on 2026-08-14. Same defect class as the
shorthand keys, through the other door.

`racerIndex`, `startRowIndex`, `indexInRow`, `finalT`, `finalRank`, `finishTime` are now written at
the call site, same names, same order.

**THE PROOF IS THE HASH, measured on both sides rather than reasoned about: the world fingerprint
`--check`ed against the record before and after, byte-identical.** The change is equivalent, so
**nothing was minted**.

**The rule went inside the existing guard (R13).** `check-fingerprint-payload.mjs` already parses
this literal, anchors on this call site and fails with this message. **And it is precise rather than
blunt:** a spread is refused when its keys are **not named at the call site**. Spreading an object
*literal* stays allowed — `...(B2_TRACE ? { b2LastInside: x } : {})` writes its key right here — so
the rule does not have to be turned off, which is how a guard dies.

Proven both directions on the real tree: `...r` back → fails and names the line; restored → passes.
Two of the guard's own tests encoded the old "spreads are a blind spot" behaviour and now state the
new rule.

**The containment guard blocked my first attempt at this commit** for quoting the live world hash in
a source comment. It was right; the comment now points at `docs/fingerprints.json`.

## PIECE 6 — the deploy workflow stops looking live

Its header has said *"NEVER RUN, and cannot run as written"* since 2026-08-04, with four blockers
enumerated. **GitHub listed it as `active` anyway** — `gh workflow list` reported
`Deploy  active  272257209`.

**A disclaimer inside a registered workflow is invisible to the platform.**

Renamed to **`deploy.yml.disabled`**. GitHub registers only `*.yml` / `*.yaml` under
`.github/workflows/`, so the suffix de-registers it entirely while the file stays exactly where a
reader looking for the deployment thinking would go, content untouched. **Nothing was made runnable
and nothing was deleted.**

**Proven at the origin rather than asserted** — after the merge, `gh workflow list --all` returns
**CI only**.

Alternatives considered and rejected: disabling through the API (repo state, invisible in the tree),
moving under `docs/` (separates it from the workflows a reader compares it against), and switching to
`workflow_dispatch` (leaves it registered **and** makes it easier to fire). Reviving it takes the
rename back **and** all four blockers cleared — written into the header, because the rename alone
would register a workflow that still cannot work.

`docs/ARCHITECTURE.md` and `docs/BACKLOG.md` corrected.
