## 8. PROPOSALS

**1. The worktree at `C:/tmp/night-sweep` should be removed, or given a `node_modules`.** It has no
`node_modules/.bin` but it *does* resolve `.githooks/`, so git will try to run a pre-commit hook into
a tree that cannot execute one. That is worse than having no hook: it fails in a way that looks like
a guard result. I removed this particular worktree as part of the cleanup, but **the shape will
recur** the next time a sweep gets its own tree. The cheap fix is a line in the sweep recipe that
either installs into the worktree or sets `core.hooksPath` to empty there deliberately.

**2. Normalise the tag register to COMMIT SHAs.** §5 shows two entries on the same commit carrying
different-looking SHAs because one records the tag object. `check-tags` cannot catch it — it reads
names. One line in `docs/TAGS.md` fixes `race-action-complete`, and a sentence in the register's
"HOW TO REGISTER A TAG" note would stop it recurring. **This is a real trap for a reader**, and it is
the same class of defect as the fingerprint copies ONE-TRUTH-2 deleted.

**3. `sweep.mjs` argues for a home for measurement drivers.** (Mine.) This one survived by luck —
a cleanup happened to look in a worktree on a scratch disk. Several documented claims in this project
rest on harnesses like it. A `scripts/sweeps/` directory, or a rule that a sweep cited in a document
must be committed before the document lands, would make the next one survive by construction rather
than by a sweep noticing. **The evidence that this is not hypothetical is that it already happened
once, to the sweep behind a claim in a shipped document.**

**4. Decide the 86 MB of sweep output.** It is regenerable by the now-archived driver, so it is safe
to delete; but regenerating it is hours of compute, and it is the raw evidence behind
LADDER-VALIDATION-1. If `wild` ever gets its full-breadth run (the open question in
[RACE-ACTION-CONTROL-1](RACE-ACTION-CONTROL-1.md)), having the `medium` cells on disk makes the
comparison cheap. **Recommendation: keep until `wild` is decided, then drop both together.**

**5. A periodic `git fsck` reading is worth having, but not as a guard.** The 383 orphans are
harmless, and a guard that fails on them would be noise. What was *worth* the look was the two
commits my memory flagged — both turned out superseded, and one corrected a stale memory. The value
was in the cross-check between the memory index and the refs, not in the orphan count. **Do this by
hand at cleanups, not on every commit.**
