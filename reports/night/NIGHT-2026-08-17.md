### The Base Speed cluster (9) — the rewrite the brief asked for

The section does not exist. The controls live under **Speed Range** inside **Race Tuning**
(`DynamicsTuningSection.jsx`), which is an advanced-tier sidebar entry — and having failed to get
there, the tests then located the two inputs **positionally**, `input[type=number]`.first()/.nth(1),
which on today's card lands on Normal Speed. Both halves had to be rebuilt.

**The numbers are no longer typed in.** The old file restated `0.00091`/`0.00118` in eight places
and the rebaseline invalidated all eight at once. The spec now **imports** `DEFAULT_BASE_SPEED_CONFIG`
and `spreadPercent` from the shipped source — both load cleanly in plain Node, checked before
relying on it — so `defaults.js` stays the one home for a default and the next rebaseline moves
these tests with it. A future disagreement between screen and default becomes a real finding instead
of a stale string.

**Stronger, not weaker, in three places:**

- `expect(color).not.toBe('')` is true of every computed colour, including the un-warned one. The
  rule the screen applies is `spread > 20 → #f59e0b`, and the fixture's ±33.3% is past it, so the
  **amber is now asserted**.
- V12 bounded the total range on both sides — `< 30` **and** `> 20` — against a default of "26%".
  The rebaseline narrowed it to 16% and the *lower* bound is what failed. A window around a number
  the test does not own was always the wrong shape; it now asserts the identity the screen renders,
  total range = 2 × spread, against `defaults.js`.
- The 2-lap gap is re-derived from `2 × (1 − min/max)` rather than hard-coded at 0.46.

**Three `data-testid` attributes were added** to `DynamicsTuningSection` — the same way
`normal-speed-input`, two controls above them, already had one. Without a name the only route to
those inputs is positional selection, which is the defect that made these tests stale in the first
place. They are invisible, they are on the Dev Screen, and `engine-reach` confirms the file cannot
reach the engine.

### The d9 lap selector (8) — a repair, with hooks the markup already offered

The report of 2026-08-16 said this cluster "needs a stable hook the markup does not offer". **That
was wrong, and worth recording:** every lap button already carries `data-testid="lap-choice-<n>"`,
the estimate carries `closed-track-estimated-duration`, and the racer-type select carries
`racer-type-select`. Nothing had to be added.

What was actually stale:

- `LAP_CHOICES` is **eight** values now — `[1,2,3,4,5,6,8,10]` — so `getByRole('button', {name:'1'})`
  matched both "1" and "10". The test also claimed "4 buttons".
- The default lap count no longer comes from a chosen duration; it comes from the **track**
  (`effectiveLaps = selectedLaps ?? trackDefaultLaps(track)`), and duration is derived from it. So
  the "auto from duration" hint does not exist — the screen says "\* track default".
- The estimate reads `Estimated duration: 87s (field 87–87s)`, not `~87s est.`.
- The open-track row states the track's **natural maximum at this race's pace** beside the estimate.
  Neither "finish line" nor "% of track" is text this screen produces. The second of those two tests
  is now where the finish line went: past the natural maximum the line is fixed and the whole field
  is slowed, and the screen says so — the test drives the slider past it and reads the warning.
- **The old test picked Rocket on a track that does not offer it.** Dirt Oval declares

### fix-list-tracks (3) — rewritten, and the fixture is not seed data

**The control is gone.** The Add-Track form has no geometry `<select>`; a track is created first and
its geometry drawn afterwards in the Track Geometry Editor, so the form says exactly that where the
dimensions used to be: "— (set after saving and drawing geometry)". Two of the three timed out
waiting for a `select` that is never rendered; the third waited for a track it had written into
`localStorage`, which stopped being where tracks live when they moved to the server.

**The decision the brief asked for — seed set or existing track — is neither, and here is why.**
Adding a "Large Test Track" to `server/seeds` would put a test fixture into every real installation's
data directory on first boot; that is production data, which the brief forbids. Rewriting against an
existing track cannot work either, because the *subject* is a track whose world is not 1280×720 and
no seeded track is one. So the fixture is **created through the run's own API and deleted again** —
the route the previous report itself identified, kept inside the test that needs it and inside this
run's isolated data directory.

The subject survives the move: `listTracks()` still returns `worldWidth`/`worldHeight`, and a track
must still show its geometry's size. Only the route moved, to the **edit** form. The third test —
the migration that repaired a track saved with stale dimensions — has no subject any more, because
a track is now ONE server record carrying its own points and its own world size; the API refuses one
without them, so there is no second copy to drift from. It asserts what replaced it: the Add form
offers no geometry selector and defers the dimensions. A selector reappearing there without the sync
would be the original defect returning.

## PIECE 2 — the mechanism, and it is not what it looked like

**The four flakes were not one spec inheriting what another left behind, and the suite's own artefact
settles it.** `client/e2e/.auth/state.json` — the browser state every test starts from — carries
exactly **two** entries: the session cookie and `racearena:lastUser`. No track cache, no geometries,
no surface classes, no config. Every test gets its own context, so nothing a spec writes can reach
another one, and the single thing they all share holds none of the keys involved.

**What it is instead: every server-backed loader in this app renders a default first and swallows a
failed fetch, and every test starts with a cold cache.**

| loader | what it does when the fetch loses |
| --- | --- |
| `trackLoader.js` → `cacheTrackGeometry` | 3000 ms timeout, `catch { return null }`, caller uses `Promise.allSettled`. The dropped geometry is invisible and the track list renders without it. |
| `surfaceClassLoader.js` → `fetchServerSurfaceClasses` | 3000 ms timeout, and on failure falls back to the localStorage cache — **empty** in a fresh context. The screen keeps the code defaults. |
| `useServerTracks` / `useSurfaceClasses` | both seed state from the cache or the code defaults and update only if the fetch succeeds. **There is no retry to wait for.** |

The consumers then read those defaults as facts. The sharpest is `handleQuickTest`:

```js
const geom = getTrack(track.geometryId);
return geom ? !geom.closed : false;     // a MISSING geometry IS a closed track
```

So an open track quick-tested with its geometry dropped runs as a **laps race**, with no error
anywhere, and the spec asserting `raceMode === 'time'` reads `'laps'` — which is precisely the
failure, reproduced and read off the artefacts twice. Ten geometry fetches per page load, seven
workers doing that at once against **one** API server, three seconds each. That is why it looked
like load, and why it looked like ordering.

**And the timing rules out the other reading.** The track buttons render from state that is set only
after the loader has settled, so a spec cannot click "too early": by the time anything is clickable
the fetches are over, and the missing data is data that **failed**, not data in flight. That is why
the repair re-navigates instead of waiting longer.

### What was changed

One new file, `client/e2e/appReady.js`, holding the mechanism and two helpers —
`ensureTrackGeometriesCached` (states the precondition the track specs had been hoping for, asking
the API which geometries exist rather than assuming) and `withServerDataRetry` (gives a
navigate-and-check block another page load). Wired into the three places that actually carry the
dependency: d9's session-data block, d11's three race-start tests, and vre-2's Reset-to-Default,
which now waits for the **Modified badge** — the statement that the browser learned about the
override at all.

**No assertion was weakened.** Every check is unchanged and must still hold; the last attempt is not
caught, so a real defect still fails on its own message. d9's session-data tests also stop seeding a
`racearena:tracks` key and two geometries that **nothing reads** — tracks come from the server, and
that dead seeding is what disguised the real dependency.

**`workers: 1` was considered and rejected**, and it was the previous report's own proposal.
Serialising would make the race easier to win without stopping a spec from depending on winning it.
A suite that passes because it is slow enough has a hidden rule exactly the way a suite that passes
in one order does — and the brief asks for isolation over ordering.

## PIECE 2b — the badge assertion was matching the label it had just typed

Round B's first new flake is **not** the dropped-fetch mechanism. It is the page-wide `getByText`
defect that this test's **sibling** was repaired for on 2026-08-16, still sitting in this one.

`getByText('Modified')` is a case-insensitive substring match over the whole page. Once the list
re-renders it resolves to **four** elements — twice for the badge, and twice for `Modified Mud`, the
label the test itself had just typed into the form. A strict-mode violation aborts an assertion
instead of retrying it, so whether it passed depended on which render the first poll caught.

It now asserts the badge **inside the row of the class under test**, and `exact` is what separates
the badge ("Modified") from the label ("Modified Mud") — without it the assertion would say nothing
the row had not already said by being found.

**And the V3 clean-up goes by label now, on both sides of the test.** `uniqueSlug` appends a suffix
when a slug is taken, so a class this test left behind would come back as `e2e-slug-test-2`: the
DELETE-by-slug that proves the derivation would 404, the leftover would stay on the **shared**
server, and the leak would grow by one every run. Deleting everything carrying the test's label
cannot miss a suffixed one.

**A tool lesson, since it cost time:** `--repeat-each` is not a valid stressor for a spec file that
mutates shared server state. Playwright schedules each repeat of a file as its own job, so three
copies of vre-2 run **concurrently** and conflict in ways a single run cannot. Its failures were the
stressor's, not the suite's.

## PIECE 3 — the audit runs without anyone remembering

Both trees are clean today — client **0 of every severity**, server **one LOW** (`body-parser`,
advisory by the gate's standing policy) — and neither stays clean, because advisories arrive on the
npm feed's timetable rather than ours.

**`.github/workflows/audit-schedule.yml`, daily at 06:17 UTC, both trees, `--report-only`.**

- **Daily**, because reachability is not knowable in advance: IP-ADDRESS-ADVISORY-1 was a
  production-reachable HIGH in the request path, and weekly would leave one like it sitting for up
  to seven days. Hourly would say the same thing to the same person twenty-four times.
- **06:17 and not 06:00**, because GitHub queues cron workloads and on-the-hour schedules are the
  most delayed.
- **Both trees through the same script** with `--tree=`, which is what SERVER-AUDIT-1 built it to
  take. No second audit script was written.

### How the owner learns that something turned red

By an **issue** on this repository, with a fixed title so it can be found again:

| state | what happens |
| --- | --- |
| findings, none open | the issue is **created**. GitHub notifies him — mail and web notification — because he watches his own repository. |
| findings, open, same set | nothing. A daily "still broken" comment is how a channel becomes noise. |
| findings, open, new set | one comment naming the new set. |
| clean, issue open | a closing comment, and the issue **closes**. Its existence mirrors the state of the trees, so "is anything outstanding?" is answered by looking at it. |

And if the job itself dies — checkout, install, or a gate that cannot parse `npm audit` — the run
goes red and GitHub mails the last editor of the workflow about a failed scheduled run. That is the
alarm for **"the audit did not happen"**, which is the one failure a report-only gate cannot report
on itself.

### Keeping a scheduled run from turning master red

Two separations, and both are needed:

1. **Its own workflow, not a `schedule:` trigger on `ci.yml`.** A schedule there would file every
   nightly result under CI, and "CI is failing" would mean two different things depending on the
   day. Here it keeps meaning exactly one: *the checks for a commit somebody pushed*.
2. **`--report-only` on both trees.** The gate prints and never exits non-zero for an advisory, so
   the job is green whenever the audit **ran**. The signal is the issue, not the build status.

**The per-push gate is untouched and still BLOCKS** on both trees, so a pull request still cannot
introduce a high/critical advisory. **The reasoning is written where the audit gate's policy already
lives** — `scripts/audit-gate.mjs` now states that it has two invokers that exist for opposite
reasons. Under R13 no new guard script was written; the existing gate gained a caller and a
paragraph.

### Proven at the origin, both directions

A notification channel nobody has ever fired is not a notification channel, so `workflow_dispatch`
takes a **`drill`** input that forces the finding verdict while still running and printing the real
audit, and labels the issue DRILL in its first line.

| dispatch | result |
| --- | --- |
| plain | green; `PASS [client]`, `PASS [server]`; *"both trees clean and nothing open — nothing to say"* |
| `drill=true` | green; issue **#140** opened |
| plain again | green; #140 commented and **CLOSED**; no open issues remain |

`gh workflow list --all` now returns **CI** and **Dependency audit (scheduled)** — and still not
`deploy`, which stays de-registered.

**The React-Router allowlist entry was not touched.** Its removal condition — a patched
react-router > 8.2.0, bumped to — is still unmet.

## PROPOSALS

1. **Make the loaders say when they lose.** Piece 2's whole mechanism is three `catch` blocks that
   return a default and log nothing: `cacheTrackGeometry`, `fetchServerSurfaceClasses`, and the
   racer-type loader. One `console.warn` naming the resource in each would have turned a night of
   inference into one line in a transcript — and would let the e2e suite assert that the app loaded
   what it needed rather than inferring it from localStorage. Cheap, invisible to the race, and it
   is the difference between a flake you can diagnose and one you cannot.

2. **Give the "no console errors" tests a named allowance list, or drop the assertion.** Three of
   d11's tests assert `errors.filter(e => !e.includes('favicon'))` is empty — a blanket claim over
   everything the browser might report, already carrying one ad-hoc exception. It is why V8 flakes
   on a 404 nobody has identified. Either the allowance becomes an explicit list, each entry with a
   reason (which is the shape the audit allowlist already uses well), or those tests assert
   something they actually own. A blanket assertion with one exception in it is a list that has not
   admitted it is a list yet.

3. **Flip the drill into a monthly self-test.** The audit's notification path is now provable on
   demand, and tonight is the only time it has ever fired. A channel proven once and then left for a
   year is a channel nobody knows is broken. One dispatch a month — or a cron on the first of the
   month with `drill` on, closing itself an hour later — keeps the proof current for the cost of two
   notifications a year.

4. **Ask the source, not the cache.** Both e2e helpers added tonight read `localStorage` to decide
   whether the app is ready, which works but couples the tests to a storage layout that is not their
   business. If the app exposed a single readiness signal — the same `waitForRacersReady()` shape
   `racer-types/index.js` already has, extended to tracks and surface classes — the specs could wait
   on the app's own word for it. That is a product change with a test-suite payoff, which is why it
   is a proposal and not a night's work.
