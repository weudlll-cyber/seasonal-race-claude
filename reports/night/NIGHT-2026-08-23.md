## The machine, and how it was split

Read before launching, as the addendum requires:

| | |
| --- | --- |
| logical cores | **14** |
| already resident | API on **4000** (1 proc), preview on **4173** (2 procs), **10** node processes, **37** browser processes |
| given to the sweep | **8 workers** |
| kept free | **6 cores** — at least two for the paper pieces' reading, grepping and doc guards, the rest as headroom for the resident processes |

**Why 8 and not more — the reasoning at launch, and it was too cautious.** The machine looked busy: a
preview server, an API and 37 browser processes resident, and an earlier run today measured a single
sim race slowing from 94 s solo to 155–190 s under five-way contention. **Measured later, the
resident processes were using under 5% of the machine** (see the correction at the foot of this
sheet), so **~6 cores sat idle all night.** 12 workers would have been the right call. **Kept here as
the decision that was actually made, not rewritten into the one I would make now.**

**How the parts are kept from spoiling each other.** The sweep runs in **its own git worktree**
(`c:/tmp/night-sweep`, branch `night/sweep-tree`), so the main tree is never switched under a running
measurement. The paper pieces own the main tree and merge there one at a time. **Before every merge
its diff is checked to touch only `docs/` and `reports/`** — never a file the sweep reads.

**A note on the machine — AND A CORRECTION I OWE YOU.** I wrote earlier that the eight sweep workers
were getting *"roughly a sixth of a core each"* and that closing the browser was **"the single biggest
thing that would speed it up"**. **Both were wrong, and you acted on the second one.**

**Measured properly, by sampling CPU over a fixed interval instead of dividing lifetime CPU by
wall-clock:** the eight workers were using **154.7 core-seconds per 20 s** — of 280 available on 14
cores — which is **very nearly a full core each**. The 36 browser processes were using **13.0**, under
5% of the machine. **After they were closed the workers used 157.1.** Nothing measurable changed.

**What I got wrong and why.** Lifetime CPU ÷ wall-clock is not a duty cycle: it averages over the
whole life of a process including time before the machine was busy, and it silently under-reports.
**The cells take ~50 minutes because a 100-race cell at 80 racers genuinely costs ~3100 s of CPU** —
not because anything was competing with them.

**The real limit is the pool size I chose: 8 workers on 14 cores, so ~6 cores sat idle all night.**
Raising it now would not help — **the critical path is a single cell** (`space-sprint`, 80 racers),
and one cell is single-threaded, so more workers cannot make it finish sooner.
